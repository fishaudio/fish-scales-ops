# GEMM performance — sm_100 / sm_103 (NVIDIA B300)

Frozen reference numbers for the block-scaled GEMM paths on sm_103. Protocol,
FLOPs conventions, shape families, M grids and the clock note: [`../README.md`](../README.md).
Tables are generated from `tests/baselines/` jsonl — do not hand-edit rows.

## Provenance and status (2026-09-22)

**Measured.** Every table in this file comes from one run on 2026-09-22,
on the B300 the maintainer granted for the day (PCI `E6:00.0` of the Kubernetes
pod named in the Environment table). The tree measured was commit `5c594cb`
plus the uncommitted MXFP8 change set, built once as a union in the virtual
environment that carries `nvidia-cutlass-dsl` 4.8.0 and verified before the
run: the nine unit suites that apply to this device pass, including the three
this change set adds cases to (`test_mxfp8_grouped`, `test_cuda_graph`,
`test_mxfp8_decode_sm100`) and `test_moe_routing_threads`, which reports `ran:
single-CTA, multi-CTA, skipped: none` on this device (the three sm_90-only
suites carry no device guard and raise the same `NotImplementedError` here as
on the previous tree); the suites pass again with each of `FSO_FC1_FUSED=0`,
`FSO_GROUPED_SLOT=0` and `FSO_DISABLE_DECODE_DSL=1` set; `compute-sanitizer
--tool memcheck` reports no error on a whole Family B MoE layer call at
M ∈ {1, 8, 64, 1024} nor on the dense `linear_mxfp8` decode band; and every
family was measured against the previous tree in the same session, alternating
trees under one GPU lock, two passes per tree on every family. 9 cells of that comparison landed outside the acceptance band.
Three of them are in fso columns and six in the torch BF16 and cuBLAS `scaled_mm` comparator columns, which contain no fso kernel and cannot move with a library change. The three fso cells are Family C `gdn_in_proj` in MXFP8 at M = 128 and M = 256 and the cubic 8192³ BSFP8 cell. At `gdn_in_proj` both trees run the identical cuBLAS `nvjet` kernel — the dense change of this set is confined to M ≤ 32, and nsys shows the same kernel at the same time per replay on both trees — and four further interleaved passes per tree put the two medians within 0.5 % of each other at M = 128, with the candidate's the lower one at M = 256, while each tree scatters 7–10 % on its own; these are the two cells the 2026-09-17 run had already recorded as scatter. The cubic cell is the 8192³ scatter described for the previous run: one of the candidate's two bench passes read 375 µs against 342 for its other pass and for both of the previous tree's, and over four further passes per tree the BSFP8 medians agree to 0.1 % (342.7 against 342.4 µs) while the candidate again shows one 365 µs outlier and the cuBLAS column measured in the same passes, which contains no fso kernel, spans 0.8 % on the previous tree and 3.6 % on this one.

The device has no clock lock available, so **every row in this file is an
unlocked-clock number** and carries the caveats in the "Unlocked device"
section below.

What this run contains that the previous one did not, stated as mechanisms:

- **A slot-bound decode route on the grouped MXFP8 GEMM, reachable from the MoE
  layer.** The pointer-array grouped kernel spends one CTA-tile on every
  (group, row-tile) pair the masked slab has, which in the decode band is
  almost all padding: at top-8 routing only a handful of the expert set can
  hold a row. A second grouped instance, in swap orientation, indexes its grid
  by a packed list of the experts that actually hold rows, and skips a tile
  whose slot is dead. Which route a call takes is decided by the host-static
  bound `max_active_groups = min(M · topk, E)` that every call site now passes:
  while the experts that can hold a row are at most three eighths of the expert
  set, the slot route is taken. The bound is host static for a given
  (M, topk, E), so a graph captured at one M stays valid for every routing draw
  at that M.
- **The packed active-expert list emitted by the routing kernel.** Building
  that list used to be a one-block kernel of the slot route's own, and before
  that each grouped GEMM needed an argument-preparation kernel. The routing
  builder already computes the histogram the list is a compaction of, so it now
  emits the list in the same launch and the slot route launches nothing but the
  GEMM. Two one-block launches per MoE layer disappear.
- **One activation quantize per token instead of one per destination.** The
  grouped activation quantizer filled each destination row of the
  `[E, m_cap, hidden]` slab by reading the token routed there, so a token
  chosen by eight experts was read and quantized eight times. It now quantizes
  each token once and scatters the result to its top-k destinations, which
  divides the read traffic and the quantize arithmetic of that stage by the
  top-k factor.
- **A fused SwiGLU epilogue on the first MoE GEMM.** FC1 used to write a
  BF16 `[E, m_cap, 2·I]` intermediate that a separate kernel then read, halved
  with silu·mul and requantized to MXFP8. A grouped instance whose epilogue
  does the silu·mul and the requantize emits the MXFP8 FC2 input directly, so
  both the intermediate and that kernel disappear. It needs gate and up weight
  rows interleaved, which is a load-time decision the library owns, and it is
  not used where the swap-orientation decode route is taken, because that
  geometry puts a token's gate and up halves in different lanes.
- **An equal-CTA tie-break in the dense wave-tile rule.** The rule picks the
  tile whose grid puts the most CTAs on the machine without spilling into a
  second wave, and a 1-SM (TileM 128) and a 2-SM (TileM 256) form of the same N
  width can tie on that count. The tie now goes to the 2-SM form, which covers
  256 rows per tile instead of 128 and therefore makes half as many passes over
  the weight matrix. Measured alone the two forms are indistinguishable,
  because an isolated dense cell replays one GEMM with its whole working set
  resident in this part's L2; inside the fused MLP block they are not, because
  `down` runs straight after `gate_up` has swept L2 and every extra pass over
  its weight is HBM traffic. The 2-SM 192-wide instance was added for this.

### Unlocked device — how to read these rows

The B300 in this pod cannot be clock-locked, so the comparability rule in
[`../README.md`](../README.md) §5 is satisfied only by the warm-up protocol and
the labelling, not by a lock. Four consequences, all measured on this device:

- **Cells at M ≥ 4096 swing by about ±3 %, not ±1 %.** The MLP block's BF16
  cell at M = 4096 was measured nine times on identical code on 2026-09-15 and
  spans 555.1 to 586.0 µs, a 5.6 % spread. Rows in that band bound the kernel
  loosely; a difference smaller than 3 % between two runs at M ≥ 4096 on this
  device is not a signal.
- **The M = 8192 cells of the MLP block are wider still, and the comparator
  columns prove it is the device.** On 2026-09-17 twelve independent worker
  processes measured that block's M = 8192 cell alone, alternating between two
  library builds. The BSFP8 column spanned 587.6 to 613.8 µs, a 4.4 % spread,
  and the two builds' medians differed by 0.1 %. The pure cuBLAS comparator
  column in the same passes — which contains no fso kernel at all and therefore
  cannot move with a library change — spanned 586.4 to 607.5 µs, the same 3.5 %.
  A change read off the M = 8192 row of [`../layer/sm100.md`](../layer/sm100.md)
  is inside the noise of the cell unless it is larger than about 8 %, so that
  row is a published number, not an acceptance unit.
- **The clock droops under sustained replay of the longest cells.** Replaying
  the M = 8192 MLP graph continuously takes the SM clock from 2032 MHz down to
  1822–1980 MHz over twelve blocks of 50 replays, with board power rising from
  228 W to 538 W; the same experiment at M = 1024 shows no droop at all. The
  M = 8192 rows are therefore measured at a lower clock than the rest of the
  grid, which is part of why their TFLOPS stop rising.
- **Small cells quantise in ~2.05 µs steps — the graph-replay tick.** Every
  small replay median on this device is an integer multiple of one tick: a
  least-squares fit over eighteen distinct medians of one dense run gives
  2.0604 µs with a worst residual of 0.135 µs (0.65 %), so the readings land on
  4.16 / 6.20 / 8.24 / 10.29 / 12.34 / 14.39 / 16.44 µs and nowhere between.
  Two things follow. A kernel improvement smaller than one tick cannot show at
  all, and when it does show it shows as a whole tick, so a cell that flips by
  one step reads as a 20–25 % change and is not one. Below M ≈ 256 most of the
  dense grid is in that regime, so those rows should be read as "at the replay
  floor" rather than compared as percentages; one cell moving one tick is not a
  signal, a run of consecutive M cells moving together is.

### Small-M caveat (all tables in this file)

Graph replay re-runs one cell's kernels with the same weights and the bench
does not flush L2, so at small M the active weights stay in the device's
126.5 MiB L2 and the µs undercut the DRAM floor. A `weight GB/s` above the
device's HBM bandwidth is L2-fed by definition — in the grouped kernel tables
below that is visible as the 3.8–5.4 TB/s plateaus, against a measured
streaming ceiling of about 6.2 TB/s. These rows bound the kernel, not the
serving cost, which rotates every layer's weights through DRAM
([`../README.md`](../README.md) §8).

### dtypes on sm_100 / sm_103

- **BF16** is the unquantized reference column (`torch.nn.functional.linear`),
  not a competitor; it is here so the FP8 columns have a truth to be measured
  against and a speed to be read against.
- **BSFP8** is block-scaled FP8 with 1×128 activation and 128×128 weight
  scales. On this arch there is no separate block-FP8 kernel: the wrapper
  expands each 1×128 scale onto the four MXFP8 1×32 tiers it covers and calls
  the MXFP8 kernel, so the GEMM that runs and the bytes it reads are the same
  as the MXFP8 row's. The two FP8 columns therefore differ only by the
  expansion step and by measurement noise, which is why they agree to a timer
  step nearly everywhere below. K % 128 and N % 128 are required.
- **MXFP8** is 1×32 UE8M0 block scales. The dense dispatcher is a three-tier
  router: cuBLAS `scaled_mm` fed fso's own packed scale buffer, the C++ CUTLASS
  cascade, and a CuTe-DSL persistent kernel. Its large-M rules were rewritten
  on 2026-09-15 — wide-N shapes (`tiles_n > 32`) go to the cuBLAS tier at every
  M, narrow-N shapes above M = 1024 go there unless the shape is long-K with a
  deep enough cascade grid, and square shapes above M = 1024 stay on the DSL
  tier's cubic table. On 2026-09-17 the wave-tile rule described above was
  added ahead of all three tiers for the band 64 ≤ M ≤ 1024: where a narrower N
  tile would put more CTAs on the machine without starting a second wave, the
  cell goes to the C++ cascade with that tile and the other two tiers decline
  it. Every cell outside the rule's bounds routes exactly as before.
- **MoE** rows are MXFP8 on the sm_100 grouped path: a CUTLASS pointer-array
  block-scaled kernel over the masked slab layout, with the per-group argument
  arrays rebuilt on device before each GEMM so one capture serves any routing.
  The captured layer is eight kernels (the six of the sm_120 layer plus one
  argument-preparation kernel per grouped GEMM); that preparation kernel is
  split around a grid-dependency barrier and both it and the GEMM are launched
  as programmatic dependent launches, so the routing-independent half overlaps
  the kernel before it. The tile rules are cascade v2: TileM = 128 in a 1×1
  cluster with TileK = 128 everywhere, a 256-wide N tile on the long-mainloop
  projection except at `m_cap ≤ 4`, the direct-store epilogue on the
  short-mainloop projection while the store is still a sliver, and — new on
  2026-09-17 — a 192-wide direct-store tile on the long-mainloop projection
  when N is a multiple of 192, the live rows per tile are still few, and the
  192-wide grid fills its last wave better than the 256-wide one. On the four
  projections in this file that last rule fires on Family B's `moe.gate_up`
  only. M = 8192 is absent from the grouped grid for the same reason as on
  sm_120: the `G × m_cap` masked slab does not fit.

`µs` is the CUDA-graph replay median (50 replays × 3 repeats, median of three);
`cos` is cosine similarity against the BF16 result on the same inputs;
TFLOPS = `2·M·N·K / µs`.

Reading (Family A): the two FP8 columns are the same kernel on this arch and
read within one timer step of each other at almost every cell, which is the
expected result of expanding the 1×128 scales onto the MXFP8 tiers rather than
running a second kernel family. Below M = 256 every FP8 column of every shape
sits between 6 and 15 µs: the problems are too small to fill 148 SMs and the
readings are on the ~2.05 µs replay grid, so BF16 occasionally reads one step
*below* the FP8 paths there (`down` at M = 64 and 128, for instance) without
that meaning anything about the kernels. From this run the M ≤ 32 band of every
shape is served by the CuTe-DSL decode row described above: the two FP8 columns
read 6.16–6.23 µs on `wqkv`, `wo` and `down` and 8.25–8.32 µs on `gate_up` at
M = 1–16, one replay tick below what the cuBLAS tier and the two-kernel split-K
cascade read on the previous tree, with `gate_up` at M = 1 in BSFP8 (9.03 µs)
and at M = 32 in MXFP8 (9.14 µs) the two cells whose two passes straddled a
tick. The wave-tile rule acts just above that band: on this family it owns
`wqkv` at M = 64, 128 and 512, `wo` at M = 64, 128 and 1024, `gate_up` at
M = 64 and 128, and `down` at M = 1024, and at those cells what sets the reading
is how many CTAs the narrower N tile puts on the machine rather than the shape's
arithmetic. The signature in the table is that such a cell reads at the same
floor as a far smaller one: `wo` is at 8.23–8.27 µs in MXFP8 at M = 32, 64,
128, 256 and 512 alike. From M = 512 upward the FP8 paths separate from BF16,
by up to 1.9× depending on the shape and the M, with the widest margins at the
top of the grid: `gate_up` at M = 8192 is 477.57 µs in BF16 against 258.67 µs

bandwidth column across a doubling of the row capacity: `moe.gate_up` reads
active weights at 5180 GB/s at M = 64 (`m_cap` 64) and at 5168 GB/s at M = 128

table shows where. It is now partitioned so that each thread stores one row
and 64 columns whatever the N tile (an EVT store, in CUTLASS's terms), and the

the expected rows per expert are at most 64. On this family `moe.gate_up`

previous tree read 47.0 and 52.4 in the same session. Above M = 2048 the weight
bandwidth falls away (3176 GB/s for `moe.gate_up` at M = 4096) because the slab

the slot-bound route, which is why they move so much there. They are not the
unit a grouped route change is accepted on — that is the whole layer in
[`../layer/sm100.md`](../layer/sm100.md) ([`../README.md`](../README.md) §8).
