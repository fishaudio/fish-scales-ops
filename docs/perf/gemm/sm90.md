# GEMM performance — sm_90 (NVIDIA H200)

Frozen reference numbers for the block-scaled GEMM paths on sm_90. Protocol,
FLOPs conventions, shape families, M grids and clock lock: [`../README.md`](../README.md).
Tables are generated from `tests/baselines/` jsonl — do not hand-edit rows.

## Provenance and status (2026-09-03; unchanged at the 2026-09-05 pause)

The 2026-09-05 sm_120 changes (UE8M0 weight scales by default, K % 128 for
block-FP8, grouped cascade rule v5) do not touch this arch: the sm_90 path
already required only K % 128, its deep_gemm kernels take FP32 scales as
before, and the Python weight quantizer keeps FP32 scales on sm_90.

Re-baseline notes (the carried-over July rows this replaced had no preserved jsonl):

- Four runs of the same dense bench at the same commit and the same `.so`. Runs 1
  and 4 ran under the system `python3`, whose process binds torch's bundled
  **NVRTC 13.0.88**; runs 2 and 3 ran under the `.dev` venv, which binds the
  system CUDA **NVRTC 13.2.78**. The sm_90 kernels are JIT-compiled in-process
  (no disk cache), so the NVRTC build is part of the result: the 13.0 runs read
  +2 % to +10 % slower on the memory-bound small-M BSFP8 cells (wo M=128 +9.5 %,
  down M=128 +7.5 %, wo M=16 +6.9 %; median +1.8 %) with the BF16 column
  unchanged, while runs within the same environment agree to a median of
  0.06 %. **Run 2 (NVRTC 13.2, the toolchain of the July tables) is the
  baseline**; run 3 reproduces it with BSFP8 median +0.1 %, p90 1.4 %, isolated
  cells up to ±5 %. Runs 1 and 4 are kept as the NVRTC-13.0 record
  (`../README.md` §8). The Family B MoE baseline (tiny_sglang `sgl` venv) and
  the Family C run (`.dev` venv) both bind NVRTC 13.2.78.
- Against the carried-over July table: BSFP8 median +0.2 % (range −2.0 % … +2.9 %,
  2 of 48 cells beyond ±2 %), MLP forward within ±0.7 % at every M. No measurable
  change of the dense sm_90 path since July.
- Same-day A/B against the July commit `a04c1b6` (built for sm_90a in a
  worktree, same bench script, same interpreter, run twice): HEAD run 2 vs
  a04c1b6 BSFP8 median −0.04 % (p10/p90 −1.4 % / +0.9 %, one cell beyond ±2 %:
  gate_up M=8192 −4.3 %, HEAD faster); HEAD run 3 vs a04c1b6 median −0.06 %.
  The two a04c1b6 runs agree with each other to median +0.04 %. The dense sm_90
  path at HEAD is equivalent to the July code within the noise floor.
- Clock under load: every busy sample of the 5 s sampler read 1830 MHz during
  run 2 and 1815–1830 MHz during the Family C run. During the A/B runs one busy
  sample read 1260 MHz at 703.7 W (the H200 700 W power cap), timed at the last
  cubic cell (16384³). The clock lock does not hold under the power cap; the
  cubic rows are unpublished for this reason too, and the family tables
  (M ≤ 8192, ≤ 1.2 ms per call) showed no such dip.
- Interpreter: the system `python3` (`~/.local` torch) also has a broken
  `torch._inductor` import that the MLP-forward bench needs; the dense and
  Family C benches ran under `/home/stone/workspace/standalone/.dev/bin/python`,
  whose torch is the same build (2.11.0+cu130, git 70d99e99). The extension was
  rebuilt for sm_90a at this commit before the runs (the previous `.so` predated
  the last `dispatch.cuh` edit by 47 s).
- Free cross-check inside the Family C run: `wo` (Family B), `wo` and
  `gdn.out_proj` (Family C) are the same 2048×4096 GEMM measured in three
  separate cells; they agree within 1 % at every M (M=8192: 114.09 / 114.06 /
  114.08 µs BSFP8).

Small-M caveat (all tables in this file): graph replay re-runs one cell's
kernels with the same weights and the bench does not flush L2, so at M ≤ 128
the active weights (10–50 MB dense, 25–50 MB grouped) largely stay in the
H200's 60 MB L2 and the µs can undercut the DRAM floor. These rows bound the
kernel, not the serving cost (`../README.md` §8).

dtypes on sm_90: BF16 = unquantized reference (`torch.nn.functional.linear`);
BSFP8 = block-scaled FP8, 1×128 activation / 128×128 weight scales, FP32
K-major scale layout, vendored deep_gemm JIT kernels (dense and grouped).
`µs` is the CUDA-graph replay median (50 replays × 3 repeats); `cos` is cosine
similarity vs the BF16 result on the same inputs; TFLOPS = `2·M·N·K / µs`.

is a fixed cost the FP8 saving cannot amortise: **BSFP8 is slower than BF16 by
1–8 % at M ≥ 512** (10.50 vs 9.72 µs at M=2048, 33.42 vs 30.92 at M=8192) and
within noise below that. A serving stack should keep this projection in BF16
