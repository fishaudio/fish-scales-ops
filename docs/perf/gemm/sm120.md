### Regression found by the 2026-09-03 re-baseline and fixed on 2026-09-04

The first sm_120 re-baseline (2026-09-03 17:29–17:45 UTC, same GPU, HEAD
`85d9c31`) failed on 69 dense BSFP8 cells: every cell whose cascade pick is the
`(TileM=64, TileN=128, Stages=4)` instantiation of the shared
`SM120BlockScaledKernel` raised `sm120 gemm kernel cannot launch: invalid
argument` (`arch/sm120/fp8/dispatch.cuh:65`). Root cause: since the July squash
`a04c1b6` the template's `SharedStorage` carried `int32_t
grouped_layout_smem[512]` (2048 B, the grouped-MoE scheduler's prefix array)
unconditionally, so every dense instantiation grew by 2 KB; a host probe
compiled with `-arch=sm_120a` gives `kSmemSize` = 102400 B for (64,128,4) vs
100352 B at `a04c1b6`, and the RTX 5090's opt-in dynamic shared memory per
block is 101376 B, so `cudaFuncSetAttribute` failed. The same 2 KB cost the
dense MXFP8 (128,64,2) instantiation 7 % at `wo` M=512 (29.0 vs 27.1 µs at
`a04c1b6`) without any launch failure. MXFP8 was otherwise unaffected (its
cascade uses Stages=2 at TileM=64 and was retuned after the change).

Fix: the array is now a builder-level opt-in (`GroupedLayoutSmem_` template
parameter on `SM120BlockScaledBuilder` and `SM120MxFP8BlockScaledBuilder`;
`SharedStorage` selects a dense or grouped layout with `cute::conditional_t`;
the staging code is under `if constexpr`); only the eight grouped MXFP8
launcher instantiations set it. Verification on C1, same day, same bench
script, against the July commit `a04c1b6` built for sm_120a on the same host:

- Every dense instantiation is back to its July `kSmemSize` (probe: (64,128,4)
  100352 B, MXFP8 (96,128,2) 62464 B); grouped instantiations keep the 2 KB.
- Unit tests (`test_correctness`, `test_mxfp8_correctness`,
  `test_mxfp8_grouped` incl. graph replay and re-routing, `test_cuda_graph`)
  pass; wqkv M=128 BSFP8 launches (cos 0.9945).
- Family A, fixed build vs `a04c1b6`: MXFP8 median +0.07 % (one cell +4.9 %,
  `wo` M=32, one timing step), BSFP8 median −0.02 % over all 56 cells, BF16
  −0.02 %. The 20 restored family cells match `a04c1b6` within ±1.5 %.
- `wo` M=512 MXFP8: 27.09 µs fixed, 27.10 µs `a04c1b6`, 29.0 µs pre-fix. The
  cascade's (128,64,2) pick is right — forcing (128,128,2) gives 36.9 µs and
  (96,128,2) 31.3 µs on both builds.
- Fixed vs pre-fix HEAD (same day): MXFP8 median −0.1 % (`wo` M=512 −7 %,
  otherwise noise), MoE B / C layer and kernel rows median 0.0 %, Family B / C
  dense and MLP forward median 0.0 %.

The earlier +8 % to +12 % gap of MXFP8 large-M cells against the carried-over
July *table* was drift of those old rows (no preserved jsonl), not code: the
July commit rebuilt today matches the fixed build within the noise floor.

### Grouped cascade rule v5 (Family C `moe.down`), 2026-09-04

A `FSO_FORCE_TILE` sweep of the grouped MXFP8 kernel cells (12 tiles × 8 M,
Families B and C) found Family B's cascade within 0.9 % of the best tile at
every cell and only one Family C cell family off its best: `moe.down`
(N=2048, K=512, a single scale-factor span) at M = 512 / 1024 / 2048, where
TileM=16 instances were 12.5 / 6.2 / 3.7 % faster **in the kernel cell**. The
rule was then decided on the **routed-layer cell** with the forced tile
restricted to the down GEMM (`FSO_FORCE_TILE_K=512`, two passes): the TileM=16
pick holds at M = 512 (em = 16, −3.7 % on the layer, −1.4 % on the routed +
shared block) and M = 640 (em = 20, −1.5 %), ties at em = 24–28, and loses at
M = 1024 (em = 32, +0.6 % with the 2-CTA/SM instance, +2.8 % with the
single-CTA one the kernel cell preferred) and M = 2048 (the kernel cell's
(16,64,4) is +16 % in the layer). Accepted rule: ≤ 4 k-tiles and em 16–24 →
(16,64,4) at 2 CTAs/SM; everything else unchanged. Effect in the tables above
and in `../layer/sm120.md`: `moe.down` M=512 214.3 → 189.6 µs (−11.5 %),
routed layer M=512 607.8 → 585.7 µs (−3.6 %), routed + shared block M=512
624.0 → 618.8 µs (−0.8 %; the shared expert's dense GEMMs run 17 µs slower
after the 2-CTA/SM down tile, still a net win); all other Family C cells and
the Family B spot check (M = 256–2048) within ±0.6 %. Why the kernel cell
mis-ranks tiles here, and the resulting acceptance rule, are in
`../README.md` §8.

Not migrated from the old `perf.md` (outside the family definition or dropped
by policy): the `gate` (N=9728) rows, the cubic M=N=K sweep, the cuBLAS
`scaled_mm` comparison columns, the triton columns of the MoE baseline, and the
RTX PRO 6000 sections (see the optional section at the end).

Small-M caveat (all tables in this file): graph replay re-runs one cell's
kernels with the same weights and the bench does not flush L2, so at M ≤ 128
the active weights (10–50 MB dense, 25–50 MB grouped) stay in the RTX 5090's
96 MB L2 and the µs undercut the DRAM floor — a `weight GB/s` above the
device's ~1.8 TB/s DRAM bandwidth is L2-fed by definition. These rows bound
the kernel, not the serving cost (`../README.md` §8). Small-M graph µs on
this device also quantise in ~2 µs steps (12.4 / 14.4 / 16.5 …), so a single
cell moving by one step between runs is not a signal.

dtypes on sm_120: BF16 = unquantized reference (`torch.nn.functional.linear`);
BSFP8 = block-scaled FP8, 1×128 activation / 128×128 weight scales, both
**UE8M0 (power-of-two)** and packed into the int32 layout the CUTLASS kernel
expects. Its cosine is 0.9992–0.9993, the same as sm_90's FP32-scale path and
as MXFP8. Tables measured before 2026-09-05 showed 0.987–0.996 and blamed
UE8M0; that was a weight-scale bug (`quantize_128x128_fp8` produced plain
`amax/448` scales, which the repack truncated to the power of two below —
every weight block dequantised 0.5–1.0× too small; `../README.md` §8).
Speed was never affected (same kernel, same bytes). K % 128 required (K % 512
before 2026-09-05; the tail scale word is zero-padded and the padded k-tiles
are TMA zero-filled — no family dense shape is affected). MXFP8 = 1×32 UE8M0 block
scales (dense and grouped). `µs` is the CUDA-graph replay median (50 replays ×
3 repeats); `cos` is cosine similarity vs the BF16 result on the same inputs;
TFLOPS = `2·M·N·K / µs`.
